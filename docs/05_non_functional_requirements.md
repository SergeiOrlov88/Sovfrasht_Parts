# 05 · Нефункциональные требования (NFR)

Требования к качеству системы — **как** она должна работать. Каждое требование измеримо и проверяемо. ID вида `NFR-<категория>-<номер>`.

---

## 1. Производительность (PERF)

**NFR-PERF-01.** Медианное время от отправки фото до готового отчёта — ≤ 30 секунд при нормальной связи (целевой KPI из док 01). 95-й перцентиль — ≤ 60 секунд.

**NFR-PERF-02.** Загрузка экрана отчёта после получения результата — ≤ 1 секунды.

**NFR-PERF-03.** Перед отправкой на сервер фото сжимается на клиенте до разумного размера (напр. ≤ 1.5 МБ, длинная сторона ≤ 2000 px) без критичной потери читаемости маркировки.

**NFR-PERF-04.** Система должна выдерживать пиковую нагрузку пилота: до ~50 одновременных сканов без деградации времени ответа сверх NFR-PERF-01.

## 2. Надёжность и доступность (REL)

**NFR-REL-01.** Целевая доступность сервиса — 99% в рабочее время пилота (не считая плановых окон обслуживания).

**NFR-REL-02.** Ни один принятый скан не теряется: при сбое распознавания скан остаётся в очереди со статусом ошибки и может быть переобработан.

**NFR-REL-03.** Внешние зависимости (vision/OCR API, каталоги) вызываются с таймаутами, повторными попытками (retry с backoff) и graceful-деградацией: при недоступности внешней модели скан ставится в очередь, пользователь получает понятное сообщение, а не ошибку.

**NFR-REL-04.** Идемпотентность: повторная отправка одного и того же скана не создаёт дублирующих заявок/результатов.

## 3. Качество распознавания (ACC)

**NFR-ACC-01.** Доля распознаваний, подтверждённых пользователем как верные, — ≥ 70–80% в поддерживаемых категориях на MVP.

**NFR-ACC-02.** Каждый результат сопровождается `confidence` и минимум одним альтернативным кандидатом (бизнес-правило из док 01). *Уточнение шага 3 (решение заказчика): кандидаты берутся только из реальных совпадений с каталогом. Если деталь в каталоге отсутствует, отчёт показывает статус `not_found` — «нет в каталоге» — и НЕ подбирает похожие позиции искусственно, чтобы выполнить это требование формально. Требование считается выполненным для деталей, представленных в каталоге.*

**NFR-ACC-03.** Результаты ниже порога достоверности не приводят к автоматическому оформлению заявки без подтверждения (человека или эксперта).

## 4. Безопасность (SEC)

**NFR-SEC-01.** Весь трафик — по HTTPS/TLS. Никаких данных в открытом виде по сети.

**NFR-SEC-02.** Пароли хранятся хешированными (bcrypt/argon2). Аутентификация — на основе токенов (JWT или сессии), с ограниченным сроком жизни и обновлением.

**NFR-SEC-03.** Авторизация по ролям (RBAC): каждый эндпоинт проверяет роль и принадлежность к организации/судну (защита от горизонтального доступа к чужим данным).

**NFR-SEC-04.** Загружаемые файлы валидируются по типу и размеру; хранилище фото закрыто от прямого публичного доступа (доступ по подписанным ссылкам с истечением).

**NFR-SEC-05.** Секреты (ключи API моделей, доступ к БД) хранятся вне репозитория — в переменных окружения/секрет-хранилище сервера. В код и Git секреты не попадают.

**NFR-SEC-06.** Ведётся аудит ключевых действий (создание заявки, решение эксперта, изменение справочника).

## 5. Приватность и данные (PRIV)

**NFR-PRIV-01.** Персональные данные пользователей минимизируются; хранятся только необходимые для работы (ФИО/логин, роль, привязка к судну/организации).

**NFR-PRIV-02.** Геопозиция скана запрашивается с явного разрешения и может быть отключена.

**NFR-PRIV-03.** Данные размещаются на сервере компании (self-hosted), что упрощает соответствие внутренним политикам.

## 6. Совместимость и связь (COMPAT)

**NFR-COMPAT-01.** PWA корректно работает в актуальных мобильных браузерах (Chrome/Safari на Android/iOS) и на десктопе. Доступ к камере через стандартный Web API.

**NFR-COMPAT-02.** Интерфейс адаптивен (mobile-first), пригоден для использования на смартфоне одной рукой, с крупными зонами нажатия (условия машинного отделения).

**NFR-COMPAT-03.** Приложение работоспособно при нестабильной/медленной связи: постановка сканов в очередь и последующая синхронизация (базово на MVP, полноценно — на нативе).

## 7. Локализация (L10N)

**NFR-L10N-01.** Интерфейс поддерживает русский язык (основной) с архитектурной готовностью к добавлению английского (интернационализация вынесена в ресурсы, не хардкод строк).

## 8. Сопровождаемость и разработка (MAINT)

**NFR-MAINT-01.** Доменная (бизнес-) логика вынесена из UI в переиспользуемый слой, чтобы миграция PWA → натив не требовала её переписывания.

**NFR-MAINT-02.** Код покрыт автотестами по критичным сценариям (распознавание-конвейер, создание заявки, RBAC). Минимальное покрытие ядра — согласовать (ориентир ≥ 60%).

**NFR-MAINT-03.** Конфигурация — через переменные окружения (12-factor), отдельные конфиги для прод/тест.

**NFR-MAINT-04.** Логи структурированные (JSON), с уровнями; ошибки распознавания трассируются до конкретного скана.

## 9. Развёртывание (DEPLOY)

**NFR-DEPLOY-01.** Приложение упаковывается в контейнер(ы) и разворачивается на существующем сервере компании рядом с «Факт Прочности» и «Пирометрикой», не конфликтуя по портам/ресурсам. *(Стек подтверждён: Python/FastAPI + Celery/Redis + PostgreSQL + React/Vite + Docker — см. док 06.)*

**NFR-DEPLOY-02.** Разделение окружений прод/тест (по образцу существующих приложений). Тест — для пилота и проверки распознавания.

**NFR-DEPLOY-03.** Обновление приложения не требует простоя пользователей сверх короткого окна; откат к предыдущей версии возможен.

**NFR-DEPLOY-04.** Внешний доступ — через существующий reverse proxy (например, Nginx) по отдельному домену/пути с TLS.

## 10. Стоимость эксплуатации (COST)

**NFR-COST-01.** Использование платных vision/OCR API контролируется: кэширование результатов по идентичным сканам, ограничение размера изображений, лимиты. Стоимость распознавания на скан отслеживается.
