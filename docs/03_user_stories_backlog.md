# 03 · User Stories, Backlog и приоритизация (MoSCoW)

Пользовательские истории сгруппированы по эпикам. У каждой истории — критерии приёмки (acceptance criteria) и приоритет MoSCoW для MVP. Это основной вход для Claude Code: одна история ≈ одна единица разработки.

Легенда приоритетов (MoSCoW для MVP): **M** — Must (без этого MVP не имеет смысла), **S** — Should (важно, но MVP выживет без этого), **C** — Could (желательно, если останется время), **W** — Won't now (сознательно отложено за пределы MVP).

Формат критериев: Given (дано) / When (когда) / Then (тогда).

---

## Эпик A — Съёмка и распознавание детали

### A1. Съёмка детали и маркировки — `M`
**Как** механик, **я хочу** сфотографировать деталь и её шильдик, **чтобы** система могла её распознать.
- Given открыт экран съёмки, When пользователь сделал хотя бы один кадр — шильдик или деталь целиком, Then кнопка распознавания активна, фото сохраняются и передаются в конвейер.
- Given в скане нет подтверждённого номера, When распознавание завершено, Then отчёт содержит опознание с пометкой «по внешнему виду» и без предложения точной закупки.
- Given камера активна, When в кадре предположительно шильдик, Then показывается подсказка «снимите табличку с номером — это повысит точность».
- Given фото размытое/тёмное, When система оценивает качество, Then предлагается переснять с указанием причины.

### A2. Гибридное распознавание (зрение + OCR) — `M`
**Как** пользователь, **я хочу**, чтобы система определила тип детали и считала маркировку, **чтобы** получить точную идентификацию.
- Given загружены фото, When запускается распознавание, Then параллельно выполняются: категоризация по изображению и OCR маркировки (номер, производитель, модель).
- Given маркировка считана, When есть номер детали, Then он используется как приоритетный ключ идентификации над визуальной категорией.
- Given распознавание завершено, When формируется результат, Then вычисляется и возвращается оценка достоверности (confidence).

### A3. Сопоставление с каталогом IMPA/ISSA/OEM — `M`
**Как** снабженец, **я хочу** получить отраслевой код детали, **чтобы** её можно было заказать у любого поставщика.
- Given есть результат распознавания, When выполняется поиск по каталогу, Then возвращается код IMPA и/или ISSA и/или OEM-номер.
- Given точного совпадения нет, When найдены близкие позиции, Then возвращается список кандидатов, отсортированный по релевантности.
- Given деталь без IMPA-кода, When есть OEM-номер, Then ключом идентификации становится OEM-номер.

### A4. Обработка при слабой связи / офлайн-очередь — `S`
**Как** механик, **я хочу**, чтобы фото не терялись при плохой связи, **чтобы** не переснимать заново.
- Given нет связи, When пользователь снимает деталь, Then фото ставятся в локальную очередь и помечаются «ожидает отправки».
- Given связь восстановилась, When приложение в сети, Then очередь автоматически синхронизируется, пользователь получает уведомление о результате.

*(Примечание: на MVP-PWA — базовая очередь через service worker; полноценный офлайн — на нативном этапе.)*

## Эпик B — Отчёт о детали

### B1. Просмотр отчёта с достоверностью — `M`
**Как** пользователь, **я хочу** видеть понятный отчёт с оценкой достоверности, **чтобы** проверить результат перед заказом.
- Given распознавание завершено, When открывается отчёт, Then отображаются: название детали, оборудование, коды (IMPA/ISSA/OEM), производитель, характеристики и confidence в процентах.
- Given confidence ниже порога, When показывается отчёт, Then выводится предупреждение и предложение отправить на подтверждение эксперту.

### B2. Аналоги и заменители — `S`
**Как** снабженец, **я хочу** видеть аналоги детали, **чтобы** выбрать по цене/сроку/наличию.
- Given деталь определена, When есть известные аналоги, Then отображается список заменителей с пометкой совместимости.

### B3. Подтверждение/исправление результата (обратная связь) — `M`
**Как** пользователь, **я хочу** отметить, верно ли определена деталь, **чтобы** улучшать систему и фиксировать корректный результат.
- Given открыт отчёт, When пользователь подтверждает или отклоняет результат, Then обратная связь сохраняется (в т.ч. для накопления датасета).
- Given пользователь отклонил результат, When он указывает правильную деталь/код, Then корректировка сохраняется как размеченный пример.

## Эпик C — Закупка

### C1. Список поставщиков с ценами и сроками — `M`
**Как** снабженец, **я хочу** видеть, где купить деталь, по какой цене и с каким сроком, **чтобы** быстро выбрать вариант.
- Given деталь определена, When открывается вкладка «Закупка», Then отображается список поставщиков/площадок с ценой, сроком и статусом наличия.
- Given источник — внешняя площадка, When пользователь выбирает вариант, Then открывается ссылка на позицию у поставщика (на MVP — курируемые/реферальные ссылки).

### C2. Оформление заявки на снабжение — `M`
**Как** механик, **я хочу** оформить заявку на деталь, **чтобы** запустить процесс закупки.
- Given открыт отчёт, When пользователь нажимает «Оформить заявку», Then создаётся заявка с деталью, кодом, судном, автором и датой.
- Given заявка создана, When она сохранена, Then она появляется в реестре и доступна снабженцу/судовладельцу.

### C3. Прямая интеграция с площадками (API прайсов/наличия) — `W`
**Как** снабженец, **я хочу** видеть актуальные цены и оформлять заказ внутри приложения, **чтобы** не уходить на внешние сайты.
- *(Отложено за пределы MVP: требует партнёрских интеграций. На MVP — курируемые ссылки.)*

---

## Эпик D — Ремонт vs замена

### D1. Рекомендация «ремонт или замена» — `M`
**Как** механик, **я хочу** понимать, дешевле восстановить деталь или заменить, **чтобы** принять решение с учётом простоя.
- Given деталь определена, When открывается вкладка «Ремонт», Then отображается рекомендация (ремонт/замена) с обоснованием и сравнением стоимости/срока.
- Given рекомендация показана, When пользователь её читает, Then выводится дисклеймер, что финальное решение — за специалистом.

### D2. Подбор ремонтных сервисов / верфей — `C`
**Как** механик/снабженец, **я хочу** найти, где восстановить деталь, **чтобы** заказать ремонт.
- Given рекомендация «ремонт», When есть доступные сервисы, Then отображается список сервисов/верфей с контактами (на MVP — курируемый список).

---

## Эпик E — Реестр и роли (флот, верфь)

### E1. Реестр деталей и заявок — `S`
**Как** судовладелец, **я хочу** видеть все заявки и детали по судам в едином реестре, **чтобы** контролировать закупки.
- Given есть заявки, When открывается реестр, Then они отображаются с фильтрами по судну, статусу, дате, категории.

### E2. Аналитика расходов по флоту — `W`
**Как** судовладелец, **я хочу** видеть аналитику расходов и повторяющихся поломок, **чтобы** оптимизировать бюджет. *(За пределами MVP.)*

### E3. Дефектная ведомость и смета (верфь) — `W`
**Как** инженер верфи, **я хочу** собирать список деталей в дефектную ведомость и выгружать смету. *(За пределами MVP; модель данных закладывается заранее.)*

### E4. Роли и права доступа — `S`
**Как** администратор, **я хочу** разграничить доступ (механик / снабженец / судовладелец / эксперт), **чтобы** каждый видел своё.
- Given пользователь авторизован, When он открывает приложение, Then функции и данные ограничены его ролью.

---

## Эпик F — Human-in-the-loop и админка

### F1. Отправка спорных случаев эксперту — `M`
**Как** пользователь, **я хочу** отправить сложный случай на подтверждение эксперту, **чтобы** получить надёжный результат.
- Given confidence ниже порога или пользователь сомневается, When он отправляет случай эксперту, Then создаётся задача на модерацию, пользователь уведомляется о сроке.

### F2. Панель оператора-эксперта — `M`
**Как** оператор-эксперт, **я хочу** видеть очередь спорных распознаваний и подтверждать/исправлять их, **чтобы** обеспечивать качество и накапливать данные.
- Given есть задачи на модерацию, When эксперт открывает панель, Then он видит фото, предложенный результат и может подтвердить/исправить код.
- Given эксперт вынес решение, When оно сохранено, Then пользователь получает результат, а корректировка идёт в датасет.

## Сводная таблица приоритетов (MoSCoW)

| Приоритет | Истории | Смысл |
|-----------|---------|-------|
| **Must** | A1, A2, A3, B1, B3, C1, C2, D1, F1, F2 | Ядро MVP: фото → код → отчёт → заявка/закупка → ремонт, с контролем качества через эксперта |
| **Should** | A4, B2, E1, E4 | Повышают ценность, но MVP работает и без них |
| **Could** | D2 | Приятное дополнение при наличии времени |
| **Won't now** | C3, E2, E3 | Требуют интеграций/партнёрств; следующий этап |

## Граница MVP (Definition of MVP)

MVP считается собранным, когда реализованы все истории уровня **Must** для одной-двух категорий оборудования (например, топливная аппаратура и насосы), включая участие оператора-эксперта. Критерий готовности качества — см. KPI в док 01 (≥70–80% подтверждённых распознаваний, медиана «фото→отчёт» ≤30 c).

## Порядок реализации (рекомендация для Claude Code)

1. Каркас приложения + аутентификация/роли (E4 частично) и модель данных.
2. Съёмка и загрузка фото (A1) + бэкенд-конвейер распознавания (A2) на готовых API.
3. Сопоставление с каталогом (A3) на узкой категории.
4. Отчёт (B1) + обратная связь (B3).
5. Закупка: список поставщиков и заявка (C1, C2).
6. Ремонт/замена (D1).
7. Human-in-the-loop: отправка эксперту и панель (F1, F2).
8. Реестр (E1), офлайн-очередь (A4), аналоги (B2) — по мере готовности.
