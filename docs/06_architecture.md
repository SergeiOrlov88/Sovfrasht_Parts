# 06 · Архитектура (C4) и развёртывание

Системная архитектура продукта **Совфрахт Детали** (`Sovfrasht_Parts`). Диаграммы в нотации C4 (уровни Context и Container) в формате Mermaid. Раздел развёртывания привязан к существующему серверу компании.

> **Статус стека: подтверждён заказчиком (31.07.2026).** Стек MVP: **Python/FastAPI + Celery/Redis + PostgreSQL + React/Vite (PWA) + Docker**, развёртывание рядом с «Факт Прочности» и «Пирометрикой» за существующим Nginx. Разделы «Стек» и «Развёртывание» ниже — целевые, не требуют дополнительного согласования.

## 1. Архитектурные принципы

Разделение фронтенда и бэкенда через REST API — чтобы MVP-PWA и будущий натив использовали один бэкенд. Доменная логика (распознавание-конвейер, правила ремонта, RBAC) вынесена из UI в сервисный слой (NFR-MAINT-01). Внешние модели (vision/OCR) изолированы за адаптерами — их можно заменить без переписывания ядра. Асинхронная обработка тяжёлых задач (распознавание) через очередь, чтобы не блокировать пользователя. Single-tenant, self-hosted на сервере компании; секреты — вне репозитория.

## 4. Поток «фото → отчёт → заявка» (последовательность)

```mermaid
sequenceDiagram
    participant U as Механик (PWA)
    participant A as Backend API
    participant Q as Очередь
    participant W as Worker
    participant V as Vision/OCR
    participant D as PostgreSQL

    U->>A: POST /scans (фото, судно)
    A->>D: Создать Scan (status=processing)
    A->>Q: Задача recognize(scan_id)
    A-->>U: 202 Accepted (scan_id)
    W->>Q: Взять задачу
    W->>V: Распознать (vision + OCR)
    V-->>W: Тип, номер, производитель
    W->>D: Сопоставить с каталогом, записать Recognition (confidence)
    alt confidence >= порог
        W->>D: status=done
    else confidence < порог
        W->>D: status=needs_review + ModerationTask
    end
    W-->>U: Уведомление «готово»
    U->>A: GET /scans/{id}/report
    A-->>U: Отчёт (деталь, коды, аналоги, поставщики, ремонт)
    U->>A: POST /part-requests (создать заявку)
    A->>D: Создать PartRequest (status=new)
```

## 5. Предлагаемый стек (подтвердить под инфраструктуру)

| Слой | Предложение | Комментарий |
|------|-------------|-------------|
| Клиент (MVP) | React + Vite, PWA (service worker), доступ к камере через Web API | Одна кодовая база, быстрый деплой без сторов |
| Клиент (цель) | Flutter или React Native | Натив для камеры/офлайн/пуш при масштабировании |
| Backend API | Python + FastAPI | Быстрая разработка, типизация, лёгкая интеграция с ML/HTTP |
| Async | Celery или RQ + Redis | Очередь задач распознавания |
| БД | PostgreSQL (+ pgvector) | Данные + векторный поиск по каталогу |
| Хранилище фото | MinIO (S3-совместимое) в docker-compose | Подписанные ссылки штатно (NFR-SEC-04); данные в периметре; как в «Факт Прочности». Переезд в облачный S3 = смена endpoint |
| Распознавание | Фронтир vision-модель через OpenRouter (основной определитель) + Yandex Vision OCR (извлечение номера), за адаптером | Все кадры скана уходят в модель одним запросом → опознание детали; OCR даёт номер для каталога; каталог обогащает, а не определяет |
| Контейнеризация | Docker + docker-compose | Рядом с существующими приложениями |
| Reverse proxy | Nginx (существующий) | Отдельный домен/путь + TLS |

> Стек подтверждён заказчиком: бэкенд на Python/FastAPI. Структура контейнеров зафиксирована.

## 7. Ключевые архитектурные решения (ADR-кратко)

**Асинхронное распознавание через очередь.** Распознавание занимает секунды и зависит от внешних API — выносим в worker, чтобы API отвечал мгновенно (202) и пользователь не ждал в блокирующем запросе.

**Адаптеры для vision/OCR.** Внешние модели меняются и дорожают; изоляция за единым интерфейсом позволяет менять провайдера и позже подключить собственную модель без изменения ядра.

**ADR-06. Vision-модель — основной определитель, каталог — обогащение (14.08.2026).**

*Контекст.* Конвейер строился как «OCR шильдика → матч по каталогу», каталог считался источником истины. На демо вскрылось: стартовый каталог (57 позиций) реальных деталей флота почти не содержит, и приложение отвечало «не найдено» вместо ответа на главный вопрос пользователя — что это за деталь.

*Решение.* Порядок ветвления перевёрнут. Vision-модель вызывается **всегда** и получает **все кадры скана одним запросом** — шильдик и общий вид вместе дают точнее, чем по отдельности. Она возвращает структуру: тип детали, производитель, модель, назначение, маркировка, достоверность, оговорки. OCR сохраняется, но его роль сузилась до извлечения номера. Каталог применяется как обогащение: совпадение по коду добавляет коды IMPA/ISSA, поставщиков и оценку ремонта и **повышает** достоверность; отсутствие позиции достоверность **не понижает**.

*Реализация.* Провайдер `OpenRouterVisionProvider` за тем же интерфейсом `VisionProvider`; один ключ OpenRouter на все фронтир-модели, конкретная модель — в `OPENROUTER_MODEL`. Режим переключается `RECOGNITION_MODE` (`vision_first` по умолчанию, `ocr_first` — прежнее поведение). Результат опознания сохраняется в `recognitions.detected_tokens` (JSON) и отдаётся в отчёте полем `identification` — миграция не потребовалась.

*Последствия.* Стоимость распознавания растёт: платный вызов идёт на каждый скан, а не только при нечитаемом шильдике — частично компенсируется кэшем по SHA-256 набора кадров (NFR-COST-01). Появляется зависимость от внешнего провайдера на основном пути, а не только на резервном; при его недоступности конвейер деградирует мягко (заглушка, NFR-REL-03). Потолок достоверности для основного пути поднят до 90 (`VISION_PRIMARY_MAX_CONFIDENCE`) против 55 у прежнего fallback — иначе каждый скан уходил бы эксперту.

*Альтернативы.* Расширять каталог до отраслевого объёма — долго и не снимает проблему незнакомых деталей. Оставить OCR основным и лишь смягчить формулировку «не найдено» — не отвечает на вопрос пользователя.

**Единый бэкенд для PWA и натива.** Вся логика — в API/сервисном слое; клиент тонкий. Это защищает инвестицию при переходе с PWA на натив.

**ADR-05. Поставщики за адаптером `SupplierProvider`.** Прямые API производителей и площадок — следующий этап (FR-PRO-05, `Won't` на MVP), но закупка проектируется под них сразу. Введён интерфейс `SupplierProvider.get_offers(part) -> list[Offer]` (`app/adapters/suppliers/base.py`) — тот же приём, что и с адаптерами vision/OCR.

На MVP работает единственная реализация `CuratedProvider`: читает предложения из таблиц `Supplier`/`SupplierOffer`, заведённых вручную. Когда появится доступ к API конкретного производителя, рядом встанет `ApiProvider` — выбор идёт через `SUPPLIER_PROVIDER` в окружении, **сервисный и доменный слои не меняются**. Тест `test_provider_swappable_without_touching_service` фиксирует это свойство: подмена провайдера на фиктивный API-источник не требует правок в `purchase_service`.

Следствия решения:
- у `SupplierOffer` есть поле `source` (`curated` / `demo` / `api`) и `fetched_at` — демонстрационные цены пилота всегда отличимы от полученных по API, и это видно в ответе `/parts/{id}/offers`;
- недоступность источника выражается отдельным исключением `SupplierUnavailable` и деградирует мягко: вкладка «Закупка» показывает «предложения временно недоступны» и не роняет отчёт целиком (NFR-REL-03);
- сортировка выдачи (сначала наличие, потом цена) живёт в провайдере, а не в API-слое, — у API-источника она может быть своей.

**Single-tenant self-hosted.** Для внутреннего инструмента Совфрахта проще, безопаснее и дешевле, чем мультитенант-облако; данные не покидают периметр компании.
