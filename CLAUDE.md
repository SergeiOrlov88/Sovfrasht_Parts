## Что это за проект

**Совфрахт Детали** (`Sovfrasht_Parts`) — приложение для распознавания судовых деталей по фотографии с рекомендациями по закупке и оценке ремонта. Пользователь фотографирует деталь и её шильдик → система определяет деталь, присваивает код IMPA/ISSA/OEM → выдаёт отчёт, варианты закупки и рекомендацию «ремонт или замена».

Контекст: внутренний инструмент компании (Совфрахт) для собственного флота и снабжения; на старте single-tenant, self-hosted. Репозиторий: https://github.com/SergeiOrlov88/Sovfrasht_Parts

## Стек (ПОДТВЕРЖДЁН заказчиком, 31.07.2026)

Развёртывание рядом с «Факт Прочности» и «Пирометрикой» на сервере компании.

- **Клиент MVP:** React + Vite, PWA (service worker), камера через Web API.
- **Backend:** Python + FastAPI.
- **БД:** PostgreSQL (+ pgvector для нечёткого поиска по каталогу).
- **Очередь:** Celery + Redis (асинхронное распознавание).
- **Хранилище фото:** S3-совместимое/диск, доступ по подписанным ссылкам.
- **Распознавание:** внешние vision/OCR API за адаптером (сменяемый провайдер).
- **Деплой:** Docker + docker-compose, за существующим Nginx, окружения prod/test.

> Стек зафиксирован — можно приступать к каркасу и бэкенду. Каталоги с исходниками именуй латиницей (`backend/`, `frontend/`, `worker/`), несмотря на кириллицу в имени корневой папки.

## Границы MVP (что делаем сейчас)

MVP = все истории уровня **Must** из `docs/03` для узкой категории оборудования (топливная аппаратура и насосы): съёмка → распознавание (vision + OCR) → сопоставление с каталогом → отчёт с confidence → закупка (курируемые ссылки + заявка) → рекомендация ремонт/замена → human-in-the-loop (эксперт).

**Не делаем в MVP** (см. `Won't` в `docs/03`): прямые API-интеграции с площадками, аналитика флота, дефектная ведомость верфи, собственная обученная модель, полноценный офлайн.

## Рекомендуемый порядок разработки

Следуй порядку из `docs/03` (раздел «Порядок реализации»):
1. Каркас + аутентификация/роли + модель данных (`docs/07`).
2. Съёмка/загрузка фото + асинхронный конвейер распознавания (адаптер vision/OCR).
3. Сопоставление с каталогом (узкая категория).
4. Отчёт + обратная связь.
5. Закупка: поставщики + заявка.
6. Ремонт/замена.
7. Human-in-the-loop: отправка эксперту + панель модерации.
8. Реестр, офлайн-очередь, аналоги — по мере готовности.

## Соглашения и правила

- **Секреты** (ключи API моделей, доступ к БД) — только в переменных окружения/`.env` (в `.gitignore`), НИКОГДА в код или Git (NFR-SEC-05).
- **RBAC**: каждый эндпоинт проверяет роль и принадлежность к организации/судну (NFR-SEC-03). Не полагайся на проверки только на клиенте.
- **Каждый результат распознавания** несёт `confidence` и минимум один альтернативный кандидат; при `confidence` ниже `CONFIDENCE_THRESHOLD` (по умолчанию 70%) — не оформлять заявку автоматически, предлагать эксперта (FR-REC-04, NFR-ACC-03).
- **Идемпотентность** создания сканов и заявок через клиентский ключ (NFR-REL-04).
- **Внешние вызовы** — с таймаутами, retry и graceful-деградацией (NFR-REL-03).
- **Доменная логика** — вне UI, в сервисном слое, чтобы PWA→натив не требовал переписывания (NFR-MAINT-01).
- **Тесты** на критичные сценарии: конвейер распознавания, создание заявки, RBAC (NFR-MAINT-02).
- **Конфигурация** — через переменные окружения; отдельные конфиги prod/test (NFR-MAINT-03).
- **Язык интерфейса** — русский, строки вынесены в ресурсы (готовность к английскому, NFR-L10N-01).
- **Время** — в UTC в БД; отображение в часовом поясе пользователя.

## Definition of Done (для фичи)

Реализованы критерии приёмки соответствующей user story; добавлены тесты на критичный путь; учтены применимые NFR (безопасность, надёжность); нет секретов в коде; обновлён `openapi.yaml` при изменении API; фича проверяется в окружении test.
